2. INSTALLATION & LOCAL DEVELOPMENT SETUP
================================================================================

Step 1: Clone the repository and navigate to backend
```sh
git clone https://github.com/SID0428/servora.git
cd servora/backend
```

Step 2: Create and activate a Python virtual environment
```sh
# macOS / Linux
python3 -m venv venv
source venv/bin/activate

# Windows (Command Prompt)
python -m venv venv
venv\Scripts\activate
```

Step 3: Install backend dependencies
```sh
pip install --upgrade pip
pip install -r requirements.txt
```

Step 4: Configure environment variables
Copy the template configuration file:
```sh
cp .env.example .env
```
For local development, no edits to `.env` are required! If `DATABASE_URL` is omitted
or left as `sqlite:///./servora.db`, FastAPI automatically initializes and runs on
the local SQLite database (`servora.db`).

Step 5: Launch the FastAPI backend server
```sh
python main.py
```
- Server URL: `http://127.0.0.1:8000`
- API Health Check: `http://127.0.0.1:8000/health`
- Interactive OpenAPI / Swagger Docs: `http://127.0.0.1:8000/docs`
- ReDoc Documentation: `http://127.0.0.1:8000/redoc`

Step 6: Launch the frontend static server
Open a separate terminal window and navigate to the `frontend/` directory:
```sh
cd ../frontend
# Serve using Python's built-in HTTP server on port 3000
python3 -m http.server 3000
```
Open your browser at `http://localhost:3000`.

3.2. Operational Access Control & Cascading Deactivation Rules
--------------------------------------------------------------
Access control is enforced at both the API controller level and the security
middleware layer (`validate_user_active_and_hierarchy` in `backend/app/security.py`):

1. Platform Admin disables Company:
   - Endpoint: `PUT /api/admin/companies/{company_id}/access` with `{ "is_active": false }`.
   - Effect: Company user is deactivated. All active sessions for the Company, all
     Franchise Branches under this company, and all Field Technicians under those
     branches are immediately terminated in `user_sessions`.
   - Block Message (Company):
     "Your company access has been disabled. Please contact the platform administrator."
   - Block Message (Branch / Tech under disabled company):
     "Your company access has been disabled. Please contact the platform administrator."

2. Company disables Franchise Branch:
   - Endpoint: `PUT /api/company/branches/{branch_id}/access` with `{ "is_active": false }`.
   - Effect: Branch user is deactivated. Active sessions for the branch and all its
     technicians are immediately revoked.
   - Block Message (Branch):
     "Your franchise access has been disabled. Please contact your company administrator."
   - Block Message (Tech under disabled branch):
     "Your franchise access has been disabled. Please contact your company administrator."

3. Franchise disables Field Technician:
   - Endpoint: `PUT /api/franchise/technicians/{technician_id}/access` with `{ "is_active": false }`.
   - Effect: Technician user is deactivated and active sessions are revoked.
   - Block Message:
     "Your technician access has been disabled. Please contact your franchise administrator."

4. Universal Password Reset / Deactivation Block:
   - Deactivated users are blocked from requesting password reset OTPs or setting new passwords.

displays an alert instructing the user of the mismatch, and redirects them to
their legitimate role-specific portal.

3.4. Background Workers (`backend/main.py`)
-------------------------------------------
1. Render Keep-Alive Worker (`keep_alive_ping_loop`):
   - Automatically wakes 45 seconds after FastAPI starts.
   - Dispatches an HTTP GET request to `/health` with User-Agent `ServSure-KeepAlive/1.0`
     every 14 minutes (840 seconds, configurable via `KEEP_ALIVE_INTERVAL_SECONDS`).
   - Prevents Render's free-tier container from idling out (which occurs at 15 minutes).
2. Multi-Tier SLA Monitor Worker (`sla_monitor_loop`):
   - Evaluates active service requests every 5 minutes (300 seconds).
   - Calls `evaluate_sla_breaches(db)` in `app/sla_engine.py`.
   - Identifies unassigned or unresolved tickets breaching SLA thresholds and auto-escalates
     them with automated alerts.

4. DATABASE MODELS & RELATIONAL SCHEMA (26 MODELS)
================================================================================
All database entities are defined in `backend/app/db/models.py`:

1. `UserModel` (`users` table):
   - `id`: String(64), Primary Key (e.g., `admin_1`, `tech_1`, UUID).
   - `name`: String(128), Nullable: False.
   - `email`: String(128), Unique, Indexed, Nullable: False.
   - `phone`: String(32), Nullable: False.
   - `role`: String(32), Nullable: False (customer, technician, branch, company, admin).
   - `password_hash`: String(255), Nullable: True (PBKDF2-SHA256).
   - `avatar`: Text, Nullable: True.
   - `address`: Text, Nullable: True.
   - `is_active`: Boolean, Default: True, Nullable: False (Set to False upon creation for company, branch, and technician accounts until first-time password setup is verified via OTP).
   - `created_at`: DateTime, Nullable: True, Default: utcnow (Auto-migrated on startup; records exact account registration timestamp).

2. `UserSessionModel` (`user_sessions` table):
   - `token_hash`: String(64), Primary Key (SHA-256 of session token).
   - `user_id`: String(64), ForeignKey("users.id", CASCADE), Indexed.
   - `expires_at`: DateTime, Indexed, Nullable: False.

3. `AuthOtpModel` (`auth_otps` table):
   - `id`: String(64), Primary Key.
   - `email`: String(128), Indexed, Nullable: False.
   - `otp_hash`: String(64), Nullable: False (SHA-256 of 6-digit OTP).
   - `expires_at`: DateTime, Nullable: False (10-minute expiry).
   - `created_at`: DateTime, Default: utcnow.
   - `user_data`: Text, Nullable: True (JSON payload for unconfirmed registrations).

4. `CompanyOnboardingModel` (`company_onboarding` table):
   - `token_hash`: String(64), Primary Key.
   - `email`: String(128), Nullable: False.
   - `name`, `phone`, `address`: Basic brand metadata.
   - `created_at`, `expires_at`: 7-day invitation expiry.
   - `otp_hash`, `otp_expires_at`: Verification OTP before setting password.
   - `password_set_at`: Timestamp when password was created.

5. `BranchOnboardingModel` (`branch_onboarding` table):
   - `token_hash`: String(64), Primary Key.
   - `company_id`: String(64), ForeignKey("users.id", CASCADE).
   - `branch_name`, `manager_name`, `email`, `mobile`, `address`, `pincode`.
   - `otp_hash`, `otp_expires_at`, `password_set_at`.

6. `CompanyBranchModel` (`company_branches` table):
   - `id`: String(64), Primary Key.
   - `company_id`: String(64), ForeignKey("users.id", CASCADE).
   - UniqueConstraint("company_id", "email").
   - `branch_name`, `manager_name`, `email`, `mobile`, `address`, `pincode`.
   - `latitude`, `longitude`: Float, Nullable: True (Physical GPS coordinates for proximity routing).
   - `opening_time`, `closing_time`: String(8) (e.g. '09:00', '19:00').
   - `slot_duration_minutes`: Integer (60, 90, 120, 180).
   - `operating_days_json`: Text (JSON array of active working days).
   - `calendar_exceptions_json`: Text (JSON map of date holiday/open overrides).

7. `TechnicianModel` (`technicians` table):
   - `id`: String(64), Primary Key.
   - `name`: String(128), Nullable: False.
   - `title`: String(128), Nullable: False.
   - `company_branch`: String(128), Nullable: True.
   - `rating`: Float, Default: 5.0.
   - `total_jobs`: Integer, Default: 0.
   - `phone`: String(32), Nullable: False.
   - `is_verified`: Boolean, Default: True.

8. `BranchTechnicianModel` (`branch_technicians` table):
   - `technician_id`: String(64), ForeignKey("technicians.id", CASCADE), Primary Key.
   - `branch_id`: String(64), ForeignKey("company_branches.id", CASCADE), Indexed.
   - `address`: Text, `pincode`: String(10).

9. `TechnicianOnboardingModel` (`technician_onboarding` table):
   - `token_hash`: String(64), Primary Key.
   - `branch_id`: String(64), ForeignKey("company_branches.id", CASCADE).
   - `name`, `title`, `mobile`, `email`, `address`, `pincode`, `otp_hash`, `password_set_at`.

10. `ApplianceModel` (`appliances` table):
    - `id`: String(64), Primary Key.
    - `user_id`: String(64), ForeignKey("users.id", CASCADE).
    - `company_id`: String(64), Nullable: True.
    - `brand`, `model_no`, `serial_no`, `category`, `appliance_name`.
    - `purchase_date`: Date, Nullable: True (Original purchase date from invoice).
    - `warranty_months`: Integer, Default: 12 (Standard catalog or brand approved duration).
    - `warranty_status`: String(32) ("Pending Verification", "Active", "Rejected", "Invoice Required", "Expired").
    - `warranty_start_date`, `warranty_end_date`: String(32).
    - `warranty_rejection_reason`: Text, Nullable: True (Brand rejection audit note).
    - `verified_at`: DateTime, Nullable: True.
    - `verified_by`: String(64), Nullable: True (User ID of brand reviewer).
    - `matched_policy_id`: String(64), Nullable: True (Fiscal year policy ID mapped by purchase date).
    - `matched_policy_name`: String(128), Nullable: True (Grandfathered policy name).
    - `policy_snapshot_json`: Text, Nullable: True (Immutable snapshot of policy coverage at registration/approval).
    - `amc_active`: Boolean, Default: False.
    - `amc_plan_name`, `amc_end_date`: String(64).
    - `invoice_url`: Text.

11. `ServiceRequestModel` (`service_requests` table):
    - `id`: String(64), Primary Key (e.g., `SR-7845`).
    - `customer_id`: String(64), ForeignKey("users.id", CASCADE).
    - `appliance_id`: String(64), ForeignKey("appliances.id", CASCADE).
    - `technician_id`: String(64), Nullable: True.
    - `branch_id`, `company_id`: String(64), Nullable: True (Strict brand franchise isolation).
    - `issue`: String(256), `description`: Text.
    - `status`: String(32) ("Request Created", "Assigned", "In Progress", "Completed", "Cancelled").
    - `latitude`, `longitude`: Float (Customer doorstep GPS location).
    - `tech_latitude`, `tech_longitude`: Float (Live technician coordinates).
    - `start_otp`: String(16) (Customer gives to tech to begin).
    - `completion_otp`: String(16) (Customer gives to tech to close).
    - `is_escalated`: Boolean, `escalation_level`: Integer (1, 2, 3).
    - `payment_status`: String(32) ("Pending", "Paid").
    - `is_outstation`: Boolean, Default: False (True when nearest brand franchise > 25.0 km).
    - `distance_km`: Float, Nullable: True (Proximity distance in km to servicing brand franchise).
    - `slot_applicable`: Boolean, Default: True (False when outstation > 25 km or no brand franchise exists).
    - `outstation_note`: String(256), Nullable: True (Customer notice explanation).

12. `JobCardModel` (`job_cards` table):
    - `id`: String(64), Primary Key (e.g., `JC-8921`).
    - `request_id`: String(64), ForeignKey("service_requests.id", CASCADE).
    - `technician_id`: String(64), ForeignKey("technicians.id", CASCADE).
    - `diagnosis`, `work_done`: Text.
    - `parts_used`: Text (JSON string of consumed parts with is_covered, coverage_type, non_coverage_reason).
    - `labor_cost`: Float.
    - `inspection_fee`: Float, Default: 299.0 (0.0 if under warranty).
    - `covered_parts_cost`: Float, Default: 0.0 (Cost of OEM-covered parts claimed to brand).
    - `customer_parts_cost`: Float, Default: 0.0 (Cost of non-covered parts/consumables billed to customer).
    - `discount_amount`: Float, Default: 0.0.
    - `cgst_amount`, `sgst_amount`: Float (9% + 9% GST on customer billable share).
    - `total_cost`: Float (Customer grand total payable).
    - `is_warranty_covered`: Boolean, Default: False.
    - `customer_signature_url`, `technician_signature_url`: Text.

13. `ServiceFeedbackModel` (`service_feedback` table):
    - `id`: String(64), Primary Key.
    - `request_id`, `customer_id`: Foreign keys.
    - `rating`: Integer (1 to 5 stars).
    - `feedback_text`: Text.

14. `SparePartModel` (`spare_parts` table):
    - `id`: String(64), Primary Key (e.g. `part_crm_cap01`).
    - `part_code`: String(64), Indexed, Nullable: False (e.g. `PART-CRM-CAP01`). Scoped uniquely per company via `UniqueConstraint("company_id", "part_code")`.
    - `name`: String(128), Nullable: False.
    - `category`: String(64), Nullable: False.
    - `brand`: String(64), Nullable: False.
    - `part_type`: String(32), Default: "functional" ("functional", "consumable", "wear_and_tear", "accessory").
    - `is_warranty_eligible`: Boolean, Default: True.
    - `warranty_component_type`: String(64), Nullable: True, Default: None (e.g. "compressor", "motor", "pcb", "magnetron").
    - `unit_price`: Float, Nullable: False, Default: 0.0.
    - `is_tax_inclusive`: Boolean, Default: False, Nullable: False (True if price is inclusive of GST/taxes; False if exclusive / tax extra).
    - `hsn_code`: String(32), Nullable: False, Default: "841890".
    - `description`: Text, Nullable: True.
    - `stock_quantity`: Integer, Default: 0, Nullable: False (Company warehouse available inventory).
    - `company_id`: String(64), ForeignKey("users.id", ondelete="CASCADE"), Nullable: True, Index: True.
    - `is_active`: Boolean, Default: True, Nullable: False.

15. `FranchiseInventoryModel` (`franchise_inventory` table):
    - `id`: String(64), Primary Key.
    - `branch_id`: String(64), ForeignKey("company_branches.id", CASCADE).
    - `part_id`: String(64), ForeignKey("spare_parts.id", CASCADE).
    - `quantity_in_stock`: Integer.
    - `min_reorder_level`: Integer, Default: 5.
    - `max_stock_level`: Integer, Default: 50.

16. `InventoryTransactionModel` (`inventory_transactions` table):
    - `id`: String(64), Primary Key.
    - `branch_id`, `part_id`: Foreign keys.
    - `transaction_type`: String(32) ("RESTOCK", "CONSUMED", "DEFECTIVE_RETURN").
    - `quantity`: Integer.
    - `unit_cost`: Float.
    - `reference_id`: String(64) (Job Card ID or PO number).

17. `WarrantyClaimModel` (`warranty_claims` table):
    - `id`: String(64), Primary Key.
    - `branch_id`, `request_id`, `appliance_id`, `part_id`: Foreign keys.
    - `claim_status`: String(32) ("Pending", "Approved", "Rejected").
    - `claim_amount`: Float.
    - `company_notes`: Text.

18. `AMCPlanModel` (`amc_plans` table):
    - `id`: String(64), Primary Key.
    - `company_id`: String(64), ForeignKey("users.id", CASCADE).
    - `plan_name`, `appliance_category`: String(64).
    - `duration_months`: Integer, `max_services`: Integer.
    - `price`: Float, `terms`: Text, `is_active`: Boolean.

19. `AMCSubscriptionModel` (`amc_subscriptions` table):
    - `id`: String(64), Primary Key.
    - `user_id`, `appliance_id`, `plan_id`: Foreign keys.
    - `start_date`, `end_date`: String(32).
    - `status`: String(32) ("Active", "Expired", "Cancelled").
    - `services_remaining`: Integer.

20. `EstimateModel` (`estimates` table):

5.6. Service Requests & Life Cycle Management (`/api/requests`)
---------------------------------------------------------------
- `GET /api/requests`: Lists requests authorized for current role.
- `GET /api/requests/available-slots`:
  - Query parameters:
    - `date` (required, string `YYYY-MM-DD`): Target appointment date.
    - `pincode` (optional, string): Customer pincode used to resolve servicing branch.
    - `branch_id` (optional, string): Servicing franchise branch ID.
    - `company_id` (optional, string): Brand company ID (enforces brand isolation).
    - `appliance_id` (optional, string): Customer appliance ID (auto-resolves brand company ID).
    - `latitude`, `longitude` (optional, float): Customer doorstep GPS coordinates for proximity calculations.
    - `request_id` (optional, string): Active service ticket ID if rescheduling (excludes this ticket's existing slot from count).
  - Strict Brand Franchise Isolation:
    - Only branches belonging strictly to the appliance's brand (`CompanyBranchModel.company_id == company_id`) are evaluated.
    - Never routes to third-party or competitor branches. If brand has zero branches registered, returns `branch_id: null, slot_applicable: false` with notice that the Brand OEM will dispatch directly.
  - Nearest Brand Franchise Proximity Engine:
    - If customer's exact PIN code has no branch, evaluates all branches of that brand.
    - Computes physical distance using the high-precision Haversine formula (when GPS coordinates exist) and India PIN code postal heuristics (same sub-district ~8 km, same district ~18 km, same state circle ~50-80 km, different zones ~180-450 km).
  - Outstation Service Radius & Slot Inapplicability (`LOCAL_SERVICE_RADIUS_KM = 25.0 km`):
    - When distance > 25.0 km: marks `slot_applicable: false`, `is_outstation: true`, returns `distance_km` and an outstation message.
    - Returns a single open appointment window: `Flexible / Outstation Visit` (rigid 1h/2h hourly capacity locks and same-day lead time cuts do not block booking).
  - Dynamic Capacity & Cutoff Calculation (for Local Visits <= 25.0 km):
    - Generated from branch operating hours (`opening_time` to `closing_time`) and duration intervals (`slot_duration_minutes`).
    - Dynamic Capacity Formula: `max(4, active_technician_count * 2)` jobs per appointment window.
    - Past Dates: Strictly blocked (`available: false, reason: "Past dates cannot be scheduled"`).
    - Calendar Overrides: Checks `calendar_exceptions_json` for store closures/holidays and `operating_days_json` for weekly offs.
    - Same-Day Lead-Time Cutoff: Requires at least 1 hour lead time before slot start (`available: false, reason: "Booking window closed for this slot"`).
    - Full Bookings: When booked >= capacity (`available: false, reason: "Fully Booked"`).
  - Returns: `{ "date": "2026-10-25", "branch_id": "br_1", "branch_name": "South Delhi Branch", "slot_applicable": true, "is_outstation": false, "distance_km": 12.2, "outstation_message": null, "slots": [...] }`.
- `POST /api/requests`:
  - Body: `{ "appliance_id": "app_1", "issue": "Water leaking", "preferred_date": "2026-10-25", "preferred_slot": "10:00 AM - 12:00 PM", "address": "...", "pincode": "...", "latitude": 28.4744, "longitude": 77.5040 }`
  - Strict Brand Isolation & Routing: Automatically invokes `find_nearest_brand_branch()`. Strictly assigns to the closest authorized franchise of that brand.
  - If brand has no registered branch: leaves `branch_id = null`, ticket goes to Brand OEM queue for manual dispatch.
  - Outstation Detection: If nearest branch is > 25.0 km away, sets `is_outstation = true`, `slot_applicable = false`, `distance_km = ...`, and `appointment_slot = "Flexible / Outstation Visit"`.
  - Validates preferred slot capacity and same-day lead time cutoff only when `slot_applicable == true`.
  - Automatically generates 4-digit start and completion OTPs.
- `POST /api/requests/{request_id}/reschedule`:
  - Body: `{ "new_date": "2026-10-26", "new_slot": "04:00 PM - 06:00 PM", "reason": "Customer unavailable" }`
  - Access Control: Customer can only reschedule their own requests; Franchise/Admin can reschedule assigned tickets.
  - Lifecycle Lock: Rescheduling is strictly rejected with HTTP 400 once doorstep service has commenced or concluded (`Service In Progress`, `Repair in Progress`, `Completed`, `Cancelled`).
  - Outstation Requests: If `slot_applicable == false` or `is_outstation == true`, allows flexible date rescheduling without failing hourly slot capacity checks.
  - Local Requests: Verifies dynamic slot availability, branch calendar exceptions, and lead-time cutoff on `new_date`.
  - Side Effects: Updates `appointment_date`, `appointment_slot`, appends `Appointment Rescheduled` event to `timeline_json`, and dispatches Brevo transactional notification (`notify_appointment_rescheduled`).

  - Automatically filters by authenticated franchise branch or technician assignments.
  - Response Schema: `List[PartSerialNumberSchema]` (`id`, `serial_number`, `part_id`, `part_name`, `part_code`, `category`, `unit_price`, `hsn_code`, `branch_id`, `branch_name`, `company_id`, `assigned_tech_id`, `assigned_tech_name`, `request_id`, `customer_name`, `appliance_name`, `status`, `assigned_at`, `installed_at`, `created_at`).
- `POST /api/inventory/serialized-parts/assign`:
  - Body: `{ "serial_number": "SN-LG-COMP-9841", "request_id": "SR-7845", "technician_id": "tech_1", "technician_name": "Ramesh Kumar" }`
  - Franchise allocation engine:
    1. Validates that the serialized unit exists in `part_serial_numbers` with `status == "in_stock"`.
    2. Transitions unit status to `"assigned_to_tech"`, recording `assigned_at`, `assigned_tech_id`, and `request_id`.
    3. Decrements franchise branch warehouse stock in `franchise_inventory.quantity_available`.
    4. Logs transaction in `inventory_transactions` (`transaction_type="tech_dispatch"`).
    5. Updates `part_requests.status` to `"Assigned"`.
    6. Automatically advances service ticket status to `"Part Assigned to Technician"` and updates live timeline step 4 with authorized doorstep installation text.
- `POST /api/inventory/serialized-parts/create`:
  - Body: `{ "serial_number": "SN-LG-COMP-9841", "part_id": "part_123", "branch_id": "branch_1" }`
  - Registers a new serialized unit into the branch warehouse inventory (`status="in_stock"`).

5.9. Warranty Claims & AMC Subscriptions (`/api/warranty-amc`)
--------------------------------------------------------------
- `GET /api/warranty-amc/registrations`:
  - Query: `?status=all|Pending Verification|Active|Rejected`
  - Returns customer appliance warranty registrations queued for the authenticated brand/company.
  - Response: list of `{ id, user_id, customer_name, customer_email, customer_phone, company_id, brand, category, model_no, serial_no, registered_on, purchase_date, warranty_months, warranty_status, warranty_start_date, warranty_end_date, warranty_rejection_reason, invoice_url, matched_policy_id, matched_policy_name, policy_snapshot_json, verified_at, verified_by }`.
- `POST /api/warranty-amc/registrations/{appliance_id}/verify`:
  - Body: `{ "action": "approve" | "reject", "warranty_months": 24, "rejection_reason": "...", "notes": "..." }`
  - Brand OEM review endpoint.
  - Approve action: Resolves fiscal year policy matched by purchase date, freezes immutable `policy_snapshot_json`, sets `warranty_status = "Active"`, overrides warranty months if specified, recalculates `warranty_start_date` and `warranty_end_date` from purchase date, logs `verified_at` and `verified_by`.
  - Reject action: Sets `warranty_status = "Rejected"`, records `warranty_rejection_reason` for customer visibility, logs `verified_at` and `verified_by`.
- `GET /api/warranty-amc/policies`:
  - Query: `?category=...&is_active=true`
  - Returns company's configured fiscal-year warranty policies with effective date windows and component warranty rules.
  - Serialization returns both `component_warranty` (parsed dictionary of component -> months, e.g. `{"compressor": 120, "motor": 60}`) and `component_warranty_json` (raw JSON string).
- `POST /api/warranty-amc/policies`:
  - Body: `{ policy_code, policy_name, category, effective_from, effective_to, comprehensive_months, consumables_covered, component_warranty_json, terms_and_conditions, is_active }`
  - Accepts `component_warranty_json` as a dictionary or JSON string. Company brand admin creates a new fiscal year warranty policy with grandfathered purchase-date coverage windows.
  - Frontend modal (`#companyWarrantyPolicyDialog`) provides 1-click Quick Presets (`+ Compressor (10 Yrs)`, `+ Motor (5 Yrs)`, `+ PCB (3 Yrs)`, `+ Magnetron (3 Yrs)`) and a `Clear` button to eliminate JSON syntax errors.
- `PUT /api/warranty-amc/policies/{policy_id}`:
  - Update policy rules, duration, component coverage, or active toggle. Returns populated `component_warranty` dictionary and `component_warranty_json` string.
- `evaluate_part_warranty_status()` Engine:
  - Centralized decision engine in `app.routes.warranty_amc` evaluating item-level coverage across Estimates (`/api/requests/{id}/estimate`) and Job Cards (`/api/requests/{id}/job-card`).
  - Decision Hierarchy:
    1. **Consumable & Ineligibility Check**: Tests catalog `part_type in ("consumable", "wear_and_tear", "accessory")` or `is_warranty_eligible == False`. Excluded unless policy explicitly specifies `consumables_covered = True`.
    2. **Comprehensive Coverage Check**: If appliance purchase date falls within `comprehensive_months` (e.g. 12m), all eligible functional parts are covered (₹0.00 customer bill, claimed from OEM).
    3. **Deterministic Component Warranty Tag Matching**: If comprehensive warranty has expired (e.g. Year 4 of AC), the engine strictly inspects `db_part.warranty_component_type` (assigned explicitly by brand OEM in inventory, e.g. `compressor`, `motor`, `pcb`, `magnetron`). If tagged, it checks appliance age vs policy duration for that tag (`age_months <= max_months`). If within limit, part is covered under OEM component warranty (₹0 customer charge); if expired, marked customer billable with reason `"Component Warranty Expired (<TAG>: <DUR>m limit exceeded)"`.
    4. **Untagged / Non-Extended Parts**: Parts without an explicit component tag (or non-covered parts like rubber bushes, brackets, or filters) default to customer billable once comprehensive warranty expires, completely eliminating false positives from part names.
- `GET /api/warranty-amc/claims`: List warranty reimbursement claims.
- `POST /api/warranty-amc/claims`: Submit parts and labor warranty claim for completed ticket (restricted to covered parts and OEM labor share).
- `PUT /api/warranty-amc/claims/{claim_id}`: Company approves or rejects warranty reimbursement.
- `GET /api/warranty-amc/plans`: List available Annual Maintenance Contract (AMC) plans.
- `POST /api/warranty-amc/subscriptions`: Customer subscribes appliance to AMC coverage.

6. SECURITY, SESSIONS & AUTHENTICATION MODEL
================================================================================
1. Password Storage:
   - Uses PBKDF2-HMAC-SHA256 with 100,000 iterations and 16-byte random salt.
   - Database hash format: `pbkdf2_sha256$100000$<salt_hex>$<digest_hex>`.
2. Session Token Architecture:
   - 64-character secure hexadecimal token generated via `secrets.token_hex(32)`.
   - Stored in `user_sessions` as a SHA-256 hash (`token_hash`).
   - Revocation: `revoke_all_user_sessions(user_id, db)` instantly removes all
     session rows for a user upon deactivation or password change.
3. OTP Generation & Verification:
   - 6-digit random number generated via `secrets.randbelow(900000) + 100000`.
   - Stored in `auth_otps` table as a SHA-256 hash (`otp_hash`) with 10-minute expiry.
   - Validated using constant-time string comparison (`hmac.compare_digest`).
4. Dual-Key Browser Storage Compatibility:
   - When saving authenticated sessions in JavaScript, keys are set across both
     `servsure_*` and `servora_*` namespaces (`servsure_user`, `servora_user`).
   - Portal `<head>` gatekeeper scripts check both namespaces, preventing accidental redirect loops.
5. User-Scoped Client Caching:
   - Client caches (e.g. requests, catalog, inventory) are strictly isolated per user ID
     (`servsure_cache_${userId}_*`) using `getUserCache(key)` and `setUserCache(key, data)`.
   - Legacy unscoped cache keys are purged upon initial load, ensuring that switching between accounts
     or role views never leaks stale tickets or spare parts.
6. URL Hash Routing Persistence:
   - Dashboard page state is synchronized with `window.location.hash` (`#Overview`, `#Requests`, `#Inventory`, etc.).
   - On page refresh or browser back/forward navigation, the active tab and data views are accurately
     restored instead of resetting or breaking navigation state.

8. TROUBLESHOOTING & OPERATIONAL GOTCHAS
================================================================================
1. "sqlite3.OperationalError: database is locked" (Local Development):
   - SQLite locks the file during write transactions. Ensure sessions are closed
     promptly with `db.close()`. For high concurrency, point to MySQL.
2. Aiven MySQL SSL Connection Errors:
   - Error: `pymysql.err.OperationalError: (3159, 'Connections using insecure transport are prohibited')`.
   - Solution: Ensure `?ssl-mode=REQUIRED` is appended to `DATABASE_URL`. The backend
     `session.py` translates this into `{ "check_hostname": False }` for PyMySQL.
3. Brevo Email HTTP 502/503:
   - Error: `Brevo is not configured. Set BREVO_API_KEY and BREVO_SENDER_EMAIL`.
   - Solution: Ensure `BREVO_API_KEY` and `BREVO_SENDER_EMAIL` are valid and the
     sender email is verified in your Brevo account dashboard.
4. Render 15-Minute Container Sleep:
   - Render free-tier spins down after 15 minutes of inactivity.
   - Solution: The autonomous background worker `keep_alive_ping_loop` pings
     `/health` every 14 minutes, keeping the container active 24/7.
5. "Role Mismatch" Redirect on Login:
   - If an operational user (e.g., technician) attempts to log in via `admin-login.html`
     or `index.html`, the client displays an alert and redirects them to their correct
     portal (`technician-login.html`).

27. Discrepancy: Cross-Company Spare Part Collision & Global Part Code Uniqueness Bottleneck
   - Initial State / Observed Issue:
     When adding a spare part in one company's portal, entering a `part_code` that matched a part already registered in another
     company caused the system to update the other company's part instead of creating a new part in the current company's
     inventory. The current company never saw the part in their dashboard, while the other company's catalog specifications
     were corrupted. Furthermore, two companies were blocked from stocking items sharing identical standard OEM or manufacturer
     part codes (e.g., standard compressor, capacitor, or valve codes).
   - Root Causes:
     1. Global Unique Constraint: In `SparePartModel`, `part_code` was configured with `unique=True`, generating a global unique
        index in SQLite (`ix_spare_parts_part_code`) that prevented any duplicate part codes across the entire database.
     2. Unscoped Part Lookup: In `add_company_spare_part` (`POST /api/inventory/company/parts`), existing parts were queried
        solely by `filter(SparePartModel.part_code == part_code)` without scoping to the authenticated company (`company_id == user.id`).
     3. Cross-Tenant Mutation: When a match was found in another company, the handler updated the foreign part's name, price, and stock,
        while leaving the foreign company's `company_id` intact, making it invisible to the creating company.
     4. Missing Company Scoping in Update Routes: `update_company_part_details` and `update_company_part_stock` did not verify
        that the target part's `company_id` matched the authenticated company's ID.
   - Resolution:
     1. Database Model & Composite Uniqueness (`backend/app/db/models.py`):
        - Removed `unique=True` from `SparePartModel.part_code` (retaining standard non-unique index).
        - Added composite constraint `UniqueConstraint("company_id", "part_code", name="uq_company_part_code")`.
     2. Automatic Database Migration (`backend/app/seeds.py`):
        - Dropped the legacy global unique index `ix_spare_parts_part_code` on SQLite.
        - Created non-unique index `ix_spare_parts_part_code ON spare_parts (part_code)`.
        - Created unique composite index `uq_company_part_code ON spare_parts (company_id, part_code)`.
        - Implemented automated data healing that restored Crompton's overwritten `part_crm_cap01` ("Dual Run Capacitor 50+5 uF")
          and preserved Samsung's part as its own distinct record (`company_id="comp_0c2b691f"`).
     3. Company-Scoped Upsert & Catalog Isolation (`backend/app/routes/inventory.py`):
        - Updated `add_company_spare_part` to query existing parts strictly scoped to `(SparePartModel.part_code == part_code, SparePartModel.company_id == target_company_id)`.
        - When creating a part, explicitly sets `company_id = user.id`.
        - In `update_company_part_details` and `update_company_part_stock`, added permission checks returning `HTTP 403 Forbidden`
          if a company attempts to modify a part belonging to another company.
        - In `get_parts_catalog` (`GET /api/inventory/parts`), scoped parts returned to franchise branches and companies based on their parent company and universal parts.
     4. Downstream Lookup Scoping (`estimates.py` & `requests.py`):
        - Scoped fallback part lookups by `req.company_id` to prevent cross-brand part matching.

28. Discrepancy: Inventory 'Edit' Action Inoperable Due to Strict ESM Assignment Exception
   - Initial State / Observed Issue:
     In `company-dashboard.html`, clicking the "⚙️ Edit" action button next to any spare part in the Central Warehouse Inventory
     table did nothing. The edit modal dialog failed to appear.
   - Root Causes:
     1. Undeclared Variable Assignment: In `frontend/js/ops-dashboard.js`, line 5156 attempted an assignment to an undeclared
        variable: `if ($editPartPrice = $("editPartPrice")) $editPartPrice.value = part.unit_price || 0;`.
     2. Strict Mode Execution: Because `ops-dashboard.js` is loaded as an ES module (`<script type="module">`), modern browsers
        execute it strictly under JavaScript Strict Mode. The assignment to undeclared `$editPartPrice` threw an unhandled
        `ReferenceError: $editPartPrice is not defined`, halting the click event listener before `showModal()` could execute.
   - Resolution:
     1. Frontend Event Listener Sanitization:
        - Replaced `$editPartPrice = $("editPartPrice")` with the standard guard:
          `if ($("editPartPrice")) $("editPartPrice").value = part.unit_price || 0;`.
     2. Backend Ownership Adoption:
        - In `update_company_part_details` and `update_company_part_stock` (`backend/app/routes/inventory.py`), ensured that if a company
          edits a part originally missing `company_id` (e.g. legacy/seed item), `part.company_id` is adopted as `user.id`.
