1. PROJECT OVERVIEW & CORE ARCHITECTURE
================================================================================
ServSure is an enterprise-grade post-sales service lifecycle platform that connects:
- Appliance Brands/Manufacturers (Companies)
- Authorized Franchise Service Centers (Branches)
- Certified Field Service Technicians
- Appliance Owners (Customers)
- Platform System Administrators

Key Architectural Decisions:
1. Static Multi-Portal Frontend (Vanilla JavaScript + Tailwind CSS via CDN):
   - Fast, zero-build compilation overhead.
   - Hosted statically on Vercel with clean rewrites (vercel.json).
   - Reusable operations master shell (ops-dashboard.js) dynamically renders
     appropriate controls, tables, and metric cards based on user role.
2. High-Performance Asynchronous Python Backend (FastAPI + SQLAlchemy + Pydantic):
   - Modular route controllers in backend/app/routes/.
   - Dual-database compatibility: local SQLite (servora.db) out-of-the-box and
     Aiven Managed MySQL with TLS in staging/production.
3. Decoupled Transactional Messaging & SLA Monitoring:
   - Email dispatch via Brevo REST API with graceful HTTP-level fallbacks.
   - Autonomous background workers for Keep-Alive pings (resetting Render idle
     timers) and 5-minute automated SLA breach detection & escalations.

2. USER ROLES & HIERARCHICAL ACCESS CONTROL
================================================================================
ServSure implements a strict 5-tier organizational hierarchy:

       +---------------------------------------------+
       |             PLATFORM ADMIN                  |
       |  (Full visibility, creates & toggles access |
       |   for Companies, L3 Escalation Handler)     |
       +----------------------+----------------------+
                              |
                              v
       +---------------------------------------------+
       |             COMPANY (BRAND)                 |
       |  (e.g., Crompton, LG; manages Franchise     |
       |   branches, warranty rules, AMC, L2 SLA)    |
       +----------------------+----------------------+
                              |
                              v
       +---------------------------------------------+
       |            FRANCHISE (BRANCH)               |
       |  (Local service hub; manages inventory,     |
       |   dispatches technicians, L1 SLA)           |
       +----------------------+----------------------+
                              |
                              v
       +---------------------------------------------+
       |             FIELD TECHNICIAN                |
       |  (Executes tickets, digital job cards,      |
       |   consumes parts, records OTP verification) |
       +----------------------+----------------------+
                              ^
                              | (Service Requests)
       +----------------------+----------------------+
       |                 CUSTOMER                    |
       |  (Registers appliances, tracks warranty/AMC,|
       |   books repairs, tracks tech in real-time)  |
       +----------------------+----------------------+

Operational Access Deactivation Rules:
- When Admin disables a Company -> Company, all its Branches, and all Technicians
  under those branches are immediately blocked from logging in or calling APIs.
  Existing user sessions are instantly deleted from user_sessions.
- When Company disables a Branch -> Branch and its Technicians are blocked.
- When Branch disables a Technician -> Technician is blocked.
- Error Messages on Blocked Access:
  - Technician: "Your technician access has been disabled. Please contact your franchise administrator."
  - Franchise: "Your franchise access has been disabled. Please contact your company administrator."
  - Company: "Your company access has been disabled. Please contact the platform administrator."

4.1. Portal Entry Points & Routing
----------------------------------
Each stakeholder has dedicated login and dashboard entry points configured with
client-side role guards:

- Customer Portal:
  - Login / Signup: frontend/index.html (routes / or /login)
  - Dashboard: frontend/customer-dashboard.html (route /customer-dashboard)
  - Guard: Checks role == 'customer'. If operational role logs in, redirects to their dashboard.

- Platform Administrator Portal:
  - Login: frontend/admin-login.html (route /admin or /admin-login)
  - Dashboard: frontend/admin-dashboard.html (route /admin-dashboard)
  - Guard: Checks role == 'admin'.

- Company / Brand Administrator Portal:
  - Login: frontend/company-login.html (route /company or /company-login)
  - Dashboard: frontend/company-dashboard.html (route /company-dashboard)
  - Guard: Checks role == 'company'.

- Franchise Branch Portal:
  - Login: frontend/franchise-login.html (route /franchise or /franchise-login)
  - Dashboard: frontend/franchise-dashboard.html (route /franchise-dashboard)
  - Guard: Checks role == 'branch' or 'franchise'.

- Technician Portal:
  - Login: frontend/technician-login.html (route /technician or /technician-login)
  - Dashboard: frontend/technician-dashboard.html (route /technician-dashboard)
  - Guard: Checks role == 'technician'. Optimized for mobile viewport screens.

4.2. Core Frontend Scripts Breakdown
------------------------------------
1. frontend/js/config.js:
   - Determines the active API URL dynamically.
   - Checks localStorage.getItem("servsure_api_url") or "servora_api_url".
   - Falls back to DEFAULT_RENDER_API = "https://servora-3v6b.onrender.com" (or http://127.0.0.1:8000 locally).
   - Exports helper functions: jsonHeaders(), authHeaders().

2. frontend/js/auth.js:
   - Controls all 5 login interfaces.
   - Handles password login (POST /api/auth/login).
   - Handles email OTP login (POST /api/auth/login-otp/request and /verify).
   - Handles Google GIS OAuth sign-in (POST /api/auth/google).
   - Universal 2-Step Forgot Password Modal:
     - Automatically attaches to any #forgotLink element across all login pages.
     - Step 1: User provides email -> calls Brevo OTP.
     - Step 2: User provides 6-digit OTP, new password, confirm password -> updates password.
   - Enforces strict portal mismatch checking: If a Technician attempts to login
     via /admin-login.html, the system alerts them and redirects to /technician-login.html.

3. frontend/js/ops-dashboard.js:
   - A single unified JavaScript engine that powers Admin, Company, Franchise, and
     Technician dashboards.
   - Dynamically checks role from the authenticated session and activates
     role-specific sidebar navigation, metrics, and data tables.
   - Features:
     - Access Toggle Switches: In Admin Companies table, Company Branches table,
       and Franchise Technicians table, toggles is_active via PUT /api/.../access.
     - In-Dashboard Change Password Accordion: In profile modal, calls POST /api/auth/change-password.
     - Profile Email Editing: Admin and Company can edit their email address via PUT /api/auth/profile.
     - Digital Job Card Builder: Technicians calculate parts, labor, GST, and capture signatures.
     - SLA Escalation Queue: Real-time SLA monitor displaying L1/L2/L3 escalations.
     - Inventory Restock & Warranty Claims review modals.

4. frontend/js/dashboard.js:
   - Powers the Customer Dashboard (customer-dashboard.html).
   - Appliance Registration with model validation, serial number deduplication, invoice uploads.
   - Real-time Service Request tracking: displays assigned technician, contact, live map simulation.
   - Warranty protection checker and AMC subscription purchase.
   - Digital job card inspection and customer rating / feedback submission.

4.3. Client-Side Session Storage & Dual-Brand Compatibility
------------------------------------------------------------
To ensure backward compatibility across prior deployments and re-branded releases,
session data is stored and checked across dual keys:
- servsure_user / servora_user: Active customer or generic session object.
- servsure_user_{role} / servora_user_{role}: Role-isolated operational session cache.
- Network requests include dual headers:
  x-servsure-user-id: <user_id> and x-servora-user-id: <user_id>.
- The backend sets both servsure_user_id and servora_user_id HTTP-only cookies.

5. BACKEND ARCHITECTURE & API SERVICES
================================================================================

5.1. FastAPI Server Setup & Background Workers (backend/main.py)
-----------------------------------------------------------------
The API is initialized with FastAPI lifecycle event handlers:
- Database Auto-Seed on Startup: Calls seed_database(SessionLocal()) inside the
  lifespan context manager to run schema migrations and seed base accounts.
- Background Worker 1: Keep-Alive Self-Ping (keep_alive_ping_loop):
  - Sends an HTTP GET request to /health every 14 minutes.
  - Keeps free-tier Render instances awake and avoids the 15-minute inactivity spin-down.
- Background Worker 2: SLA Monitor Loop (sla_monitor_loop):
  - Executes every 5 minutes.
  - Calls evaluate_sla_breaches(db) in app/sla_engine.py to identify tickets
    exceeding response or resolution thresholds and auto-escalates them.

5.3. Database Session & Connection Architecture (backend/app/db/session.py)
-----------------------------------------------------------------------------
- Handles SQLite vs MySQL connections automatically.
- For Aiven MySQL (mysql+pymysql://...):
  - Translates ?ssl-mode=REQUIRED to PyMySQL's SSL dictionary { "check_hostname": False }.
  - Configures connection pool: pool_size=10, max_overflow=20, pool_recycle=3600, pool_pre_ping=True.
- Session dependency: get_db() yields a SessionLocal() and closes it after the request.

5.5. Security, Sessions & Hierarchical Access Engine (backend/app/security.py)
--------------------------------------------------------------------------------
- Session Tokens:
  - Cryptographic 64-character hex tokens signed with secret and timestamp.
  - Stored in user_sessions table hashed with SHA-256 (token_hash).
- Password Hashing:
  - Uses PBKDF2-HMAC-SHA256 with 100,000 rounds and random 16-byte salt:
    pbkdf2_sha256$<rounds>$<salt_hex>$<digest_hex>.
- validate_user_active_and_hierarchy(user, db):
  - Checked on every authenticated request and login attempt.
  - Step 1: Checks user.is_active. If False, raises 403 and calls revoke_all_user_sessions(user.id, db).
  - Step 2: For Technicians, checks if their assigned Branch is active. If not, raises 403.
  - Step 3: For Technicians and Branches, checks if their parent Company is active. If not, raises 403.
- revoke_all_user_sessions(user_id, db):
  - Immediately deletes all active rows in user_sessions for that user.

5.6. Transactional Email Service (backend/app/email_service.py)
----------------------------------------------------------------
- Sends email notifications via Brevo API (https://api.brevo.com/v3/smtp/email).
- Requires BREVO_API_KEY and BREVO_SENDER_EMAIL.
- Handles connection errors and raises informative HTTP 502/503 errors if delivery fails.

5.7. Notification Engine & Multi-Tier SLA Scanner (backend/app/sla_engine.py)
-------------------------------------------------------------------------------
SRS 6.15 SLA Evaluation Rules:
1. Unassigned Ticket Breaches:
   - > 4 Hours Unassigned  -> Level 1 Escalation to Franchise Branch
   - > 8 Hours Unassigned  -> Level 2 Escalation to Brand Company Manager
   - > 12 Hours Unassigned -> Level 3 Escalation to Platform Admin
2. Resolution Time Breaches:
   - > 48 Hours Unresolved -> Level 1 Escalation to Franchise Branch
   - > 72 Hours Unresolved -> Level 2 Escalation to Brand Company Manager
   - > 96 Hours Unresolved -> Level 3 Escalation to Platform Admin
When an escalation triggers, an EscalationModel row is created, ticket status is
marked is_escalated = True, and an automated email/SMS alert is logged.

6. API ROUTE REFERENCE & ENDPOINTS
================================================================================

6.1. Authentication Routes (backend/app/routes/auth.py)
---------------------------------------------------------
- POST /api/auth/login:
  - Payload: { email, password, role }
  - Validates credentials against PBKDF2 hash (or demo password), checks active status,
    creates user session, sets HTTP-only cookies, returns user profile.
- POST /api/auth/login-otp/request:
  - Payload: { email }
  - Generates 6-digit OTP, stores hash in auth_otps, sends email via Brevo.
- POST /api/auth/login-otp/verify:
  - Payload: { email, otp }
  - Verifies OTP hash and expiry, returns authenticated session.
- POST /api/auth/google:
  - Payload: { credential, role }
  - Verifies Google GIS ID token, auto-provisions customer account or signs in.
- POST /api/auth/forgot-password/request-otp:
  - Payload: { email }
  - Sends 6-digit password reset OTP to registered email. Rejects inactive accounts.
- POST /api/auth/forgot-password/reset:
  - Payload: { email, otp, new_password }
  - Validates OTP, hashes new password with PBKDF2, revokes all existing sessions.
- POST /api/auth/change-password:
  - Payload: { current_password, new_password }
  - Requires authenticated session. Verifies current password, updates to new password.
- PUT /api/auth/profile:
  - Payload: { name, phone, address, email? }
  - Updates profile. email field is only accepted and updated for admin and company.
- GET /api/auth/me:
  - Returns the currently authenticated user's profile and active role.
- POST /api/auth/logout:
  - Revokes current session token and clears auth cookies.

6.2. Platform Administration Routes (backend/app/routes/admin.py)
-------------------------------------------------------------------
- GET /api/admin/metrics: Platform-wide stats (total companies, branches, tickets, revenue).
- GET /api/admin/companies: List all registered brand companies with status.
- POST /api/admin/companies: Onboard new company & send password setup email.
- PUT /api/admin/companies/{company_id}/access:
  - Payload: { is_active: boolean }
  - Enables or disables company access. Hierarchically invalidates all sessions.

6.3. Brand / Company Routes (backend/app/routes/company.py)
-------------------------------------------------------------
- GET /api/company/metrics: Brand-specific ticket volumes, active branches, SLA rates.
- GET /api/company/branches: List all franchise branches under this brand.
- POST /api/company/branches: Onboard a new franchise branch & email setup link.
- PUT /api/company/branches/{branch_id}/access:
  - Payload: { is_active: boolean }
  - Enables or disables branch access. Hierarchically invalidates branch & tech sessions.

6.4. Franchise Branch Routes (backend/app/routes/franchise.py)
----------------------------------------------------------------
- GET /api/franchise/metrics: Branch ticket queue, technician availability, parts stock.
- GET /api/franchise/technicians: List all technicians assigned to this branch.
- POST /api/franchise/technicians: Onboard new field technician & email setup link.
- PUT /api/franchise/technicians/{technician_id}/access:
  - Payload: { is_active: boolean }
  - Enables or disables technician access and revokes active sessions.

6.5. Field Technician Routes (backend/app/routes/technician.py)
-----------------------------------------------------------------
- GET /api/technician/jobs: List assigned service requests for logged-in technician.
- POST /api/technician/jobs/{request_id}/start: Verifies start OTP provided by customer.
- POST /api/technician/jobs/{request_id}/complete:
  - Submits digital Job Card (parts consumed, labor fee, diagnosis).
  - Verifies customer completion OTP, captures signatures, finalizes ticket.
- POST /api/technician/location: Updates real-time GPS coordinates for live customer tracking.

6.6. Customer Requests, Appliances & Job Cards
----------------------------------------------
- GET /api/requests: List requests filtered by user role and authorization scope.
- POST /api/requests: Customer books new service ticket.
- GET /api/appliances: List customer registered appliances with warranty status.
- POST /api/appliances: Register new appliance with serial number validation.
- GET /api/requests/{request_id}/job-card: Retrieve finalized digital job card and receipt.

7. STEP-BY-STEP LOCAL DEVELOPMENT SETUP
================================================================================

Prerequisites:
- Python 3.11 or higher
- Modern web browser (Chrome, Edge, Firefox, Safari)

Step 1: Navigate to the backend directory
  cd backend

Step 2: Create and activate a Python virtual environment
  # macOS / Linux
  python3 -m venv venv
  source venv/bin/activate

  # Windows (Command Prompt)
  python -m venv venv
  venv\Scripts\activate

Step 3: Install backend dependencies
  pip install -r requirements.txt

Step 4: Run the FastAPI backend server
  python main.py

  - The backend will start at http://127.0.0.1:8000.
  - It will automatically create servora.db (SQLite) and run all schema migrations.
  - You can inspect the interactive Swagger API documentation at:
    http://127.0.0.1:8000/docs

Step 5: Run the Frontend
Because the frontend is static HTML/CSS/JS, serve it with any static server:
  # Open a new terminal in the frontend directory:
  cd frontend

  # Using Python's built-in static server:
  python3 -m http.server 3000

Open http://localhost:3000 in your web browser.

8. PRODUCTION DEPLOYMENT (RENDER, VERCEL, AIVEN MYSQL)
================================================================================

8.1. Database Setup on Aiven MySQL
----------------------------------
1. Create a MySQL service on Aiven (or AWS RDS / Google Cloud SQL).
2. Copy the SQLAlchemy connection URI.
3. Replace the driver prefix with mysql+pymysql://:
   mysql+pymysql://avnadmin:PASSWORD@HOST:PORT/defaultdb?ssl-mode=REQUIRED

8.2. Deploying Backend to Render
--------------------------------
1. In Render, create a new Web Service connected to your repository.
2. Root Directory: backend

   ```python
       payload: CustomPayload,
       db: Session = Depends(get_db),
       current_user: UserModel = Depends(get_authenticated_user)
   ):
       # Role authorization check
       if current_user.role != "company":
           raise HTTPException(status_code=403, detail="Unauthorized")
       # Business logic...
       return { "status": "success" }
   ```

9.2. Adding a Database Column / Running Migrations
-------------------------------------------------
1. Add the new Column to the model in backend/app/db/models.py.
2. Because production uses an existing database, add an idempotent migration check
   in backend/app/seeds.py:
   ```python
   table_columns = {col["name"] for col in inspect(engine).get_columns("table_name")}
   if "new_column" not in table_columns:
       with engine.begin() as connection:
           connection.execute(text("ALTER TABLE table_name ADD COLUMN new_column VARCHAR(64) NULL"))
   ```
3. Test locally by running python main.py.

10. CODING CONVENTIONS, GOTCHAS & BEST PRACTICES
================================================================================
1. Never Remove validate_user_active_and_hierarchy:
   - Every sensitive or state-changing endpoint must call validate_user_active_and_hierarchy.
   - This ensures deactivated companies, branches, or technicians cannot perform actions.
2. Preserving Dual Branding Compatibility:
   - When reading or setting local storage items in JavaScript, maintain fallback
     support for servsure_* and servora_* keys.
3. Password Handling:
   - Always hash passwords using make_password_hash (pbkdf2_sha256$).
   - Never store plain-text passwords in the database.
4. Email Delivery:
   - The platform treats Brevo configuration strictly. If Brevo credentials are
     missing or misconfigured during onboarding or OTP requests, an informative
     HTTP error is raised to the client rather than failing silently.
5. SQLite vs MySQL Data Types:
   - Use standard SQLAlchemy types (String(64), Integer, Float, Boolean, DateTime).
   - Avoid engine-specific types like MySQL ENUM or JSON functions to ensure 100%
     compatibility between local development (SQLite) and production (MySQL).
